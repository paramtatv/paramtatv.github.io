Past 2 GIPS — Sassembly runs natively at 2.25 billion instructions a second

2026-10-14 · Paramtatva sassemblyperformancerisc-vnative

संस्कृतम् हिन्दी

Sassembly is a programming language written entirely in Sanskrit. Its keywords are Sanskrit words, its operand roles are marked by kāraka sigils (the grammatical case endings of Sanskrit) instead of by position or punctuation, and it compiles to RISC-V RV64. Its compiler is written in Sassembly and, compiled by itself, reproduces itself byte for byte.

This post is about how fast that compiler runs.

The headline: 2.25 G guest instructions per second

We measured the Sassembly compiler on its heaviest everyday job: working through its own source, all 5.36 MB of it, in one run. That run executes 56,353,729,585 RISC-V instructions: fifty-six billion steps of real compiler work.

On the native path the whole run took 24.94 seconds of CPU time on an Intel Core i9-9900X. That is 2.25 billion guest instructions per second, past the 2 GIPS mark, on the program that matters most to us: the compiler itself.

Before measuring, we wrote down an expected band for compiler-style code of 0.25 to 1.0 G instructions per second. Compiler code with its branches, calls and memory traffic usually translates less well than a tight loop. The measured rate came in above the whole band. The compiler runs close to the rate of our simple benchmark loops.

What "native" means here

A Sassembly program compiles to an ordinary RV64 machine image. There are two ways to run that image:

  • The interpreter, which steps through it one RISC-V instruction at a time. It is our reference machine: simple, exact, and the yardstick everything else is checked against.
  • The native path, where a translator rewrites the RV64 image ahead of time into the host's own machine code, x86-64 or AArch64, and the host CPU then runs it directly. The translator exists in Sassembly too; the timed runs here used its byte-identical twin, which emits exactly the same machine code.

The same 56-billion-instruction compiler run that takes 24.94 seconds natively takes 848.7 seconds under the interpreter (66 million instructions per second). Native is more than 33 times faster on identical work.

A tight loop, counted exactly

We also measured a small generated benchmark that runs 2.0 billion guest instructions. Natively it finishes in 1.05–1.09 seconds of CPU time, about 1.87 G instructions per second on the same Intel machine.

On that loop we counted host instructions directly by single-stepping the native code. In steady state the translator emits exactly 3.000 host instructions per guest instruction: 24 host instructions for each 8-instruction iteration. For the compiler's own start-up and a small "hello" compile the ratio is 3.13. The translation stays lean on real code as well as on loops.

The same speed on Arm

The translator also targets AArch64. On an Arm Cortex-A78AE core clocked at 2.2 GHz, the same 2-billion-instruction benchmark runs in 1.023 seconds: 1.95 G guest instructions per second, or 0.89 guest instructions per clock cycle. Nearly one RISC-V instruction completes per Arm clock cycle.

Where the time goes

We sampled the native compiler run every 2 ms (12,753 samples) to see where the cycles land. About half of the time goes to guarded memory access, the loads and stores themselves together with the address calculation and guard check the translator places before each one. Plain arithmetic and logic account for 28%, calls for about 15%, and indirect jumps through the runtime for only about 2%.

Why this matters

A language that hosts its own compiler is only as pleasant as that compiler is fast. With the native path the full self-compile workload finishes in under half a minute on a desktop CPU, and the same benchmark runs at nearly the same rate on Arm. Sassembly programs, and the compiler that builds them, run at real hardware speed.

We are building toward more: faster memory paths, more host targets, and the same per-cycle efficiency on every machine Sassembly runs on.
